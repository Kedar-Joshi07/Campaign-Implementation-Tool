# Interface and data contract for all lanes

Freeze these conceptual names in 14B_01; if actual repository naming differs, publish one machine-readable agreed contract and update all consumers together. Existing public schemas remain intact.

V3 request: `selection_contract_version="3"`, `score_semantics="PRODUCT_BUYER_SIMILARITY"`, `similarity_minimum` from approved finite set, normalized `campaign_context`, normalized `targeting_criteria`, `selection_mode`, optional explicit `top_n`, `catalog_version`. No `propensity_bucket` or probability filters in v3. Reject mixed, ambiguous, unsupported, NaN, infinite, bool-as-numeric, stale catalog, and unknown semantics. Existing unversioned request behavior is characterized and preserved.

V3 preflight: common contract + demographic_eligible_count, valid_similarity_count, invalid_similarity_count, similarity_qualifying_count, selected_count, similarity_currentness (CURRENT/STALE/UNVERIFIED/NOT_AVAILABLE), similarity_eligibility (ELIGIBLE/NOT_ELIGIBLE), bounded reason_code, build_available, profile IDs/hash, composite-context hash, generation_id, score_method_version, source identities, snapshot-bound cutoff/version. For absent score artifacts counts are null/unknown, not zero. Probability support has separate optional eligibility/currentness; never reuse the v2 calibration field to mean similarity readiness.

Preflight can provide demographic counts before intelligence exists. Build request must be reachable: bounded prepare/resume action creates/rejoins the exact v3 intelligence dependency, reports BUILDING until verified, then allows current exact preflight. No requirement to pass a similarity count before building the score artifact needed to count it. Submission may save a queued dependency-backed run under existing architecture; stage 01 fixes one coherent path in tests.

Profile artifact identity includes product, historical context + resolved window, buyer conversion definition, customer/sales imports/checksums, common feature hash, similarity method/preprocessor parameters, fit/holdout union identity hashes, version, seed, prototype support and serialization checksum. Score generation adds demographic import identity/checksum, reference date, exact profile/composite hash and scorer version. Similarity does not depend on v2 calibration identity.

Score tables: one valid or explicitly invalid row per person per product/generation; valid score finite [0,1], feature coverage [0,1], prototype key internal, reason nullable only for valid rows, mutually exclusive valid/invalid state. Composite winners can be materialized once per verified product set or resolved through a streaming indexed aggregate. Do not create 5M rows per UI threshold or channel. Generation staging rows cannot be reused as ready. Unique constraints prevent duplicate people per product/generation; immutable published rows cannot be overwritten.

Membership v3 minimum: person_id, buyer_similarity_score, similarity_tier, matched_product_id, score_method_version, feature_coverage, similarity_generation_id. Shared header metadata holds selection/profile/source contracts and checksums. Optional purchase probability is nullable and has separate provenance/currentness, or omitted entirely for this membership version; never fill missing with 0. No customer ID/PII in analytical membership. Do not overload raw_propensity_score, probability_bucket, percentile_bucket, rank_band, or calibrated_purchase_probability with similarity.

Cache identity: selection and membership version, score semantics/method, threshold predicate type and threshold, product match policy and normalized products, profile/composite/generation hash, source/import identities, catalog, normalized criteria/branches, selection_mode/top_n, ordering policy, publication cutoff. Optional display-only probability does not alter similarity membership; if snapshotted, its exact lineage must bind the payload's cache identity. Legacy v1/v2 keys remain stable.

Invalidation matrix: customer/sales replacement → dependent profiles and scores stale; demographic replacement → scores/preflight/results/export currentness stale; product taxonomy/context policy/method change → affected artifacts stale; v2 calibration promotion → probability artifacts/display only; threshold change → new search/cache, not retraining; delivery channel change → existing analytical intelligence reusable where the context is otherwise identical, contact export/profile remains channel-specific. Latest-source equality is authoritative even if a best-effort invalidation callback failed.

V3 channel exports require a declared new export/profile version or versioned analytical projection because the current base headers assume propensity_score and ranking metadata. Preserve old headers; do not fabricate legacy score/rank fields. Bind profile/export version in request and registry metadata and reuse existing contact/consent rules.
